Case study · 2024 · Personal · Team project · Shipped

Search that forgives typos.

Most contact managers require exact matches. Type "Moamed" for "Mohamed" and you get nothing. ContactsManager uses Levenshtein edit distance so a partial or typo'd query returns the closest matches, sorted by similarity.

Role Backend / Database Duration 2024 Team 6 engineers · ProGeeks Stack Java · Swing · SQLite Status Shipped

The problem

Contacts search should handle the way people actually type.

Every contact app I had used required the query to match a field exactly. Real queries are partial, misspelled, or phonetically approximated. Users reach for a name before they have typed it perfectly, so a search that requires exactness is a search that fails half the time. ContactsManager treats search as approximate matching, not exact filtering.

The approach

What I built.

  • Java desktop application — Swing for the UI, SQLite for persistence.
  • Search by name, phone, or email. Closest matches sorted first.
  • Levenshtein edit distance as the similarity metric.
  • Full CRUD on contacts — create, read, update, delete.
  • Six-person team. I owned the backend and the database layer. The UI and search algorithm were split across the team.

Technical deep dive

The choices that shaped it.

For engineers. The decisions behind the architecture, written down.

ADR-001Search

Levenshtein edit distance over prefix matching

Problem
Contacts search needs to handle typos and partial matches. Prefix matching fails when the first letter is wrong, which is common in real queries.
Options
Exact match · prefix match · substring match · Levenshtein edit distance.
Choice
Levenshtein. Every query is compared against every contact, and the closest matches are returned in order.
Consequence
Misspelled queries still surface the right contact. A query for "Moamed" finds "Mohamed" ranked ahead of unrelated entries.
Rejected because
Prefix matching was simpler and faster, but it failed on transposed letters, missing vowels, and any query that did not start with the right letter. On a contact list, that is most queries.

Lessons learned

What I'd do differently.

The honest section. Every project has one.

01

Small data sets hide algorithmic cost

Levenshtein is O(nm) per comparison, which sounds expensive until you realize the contact list is small enough that it does not matter. Sometimes the "slower" algorithm is the right one because the actual bottleneck is elsewhere.

02

Splitting responsibilities needs a written contract

The team split the work into UI and data layers. Without a written interface between them, integration took longer than it should have. The lesson carried into every project after this one.

FAQ

Common questions.

What is ContactsManager? + −

A Java desktop contact manager with fuzzy search. Search by name, phone, or email, and the closest matches are returned first using Levenshtein edit distance.

Why Levenshtein and not something simpler? + −

Because the failure mode of simpler matching is real: prefix and exact search both fail on typos, which are common in real queries. Levenshtein handles the cases that matter, and the contact list is small enough that the computational cost is irrelevant.

Was it a solo project? + −

No. It was a six-person team project. The repository is com.ProGeeks.ContactsManager, and all six contributors are listed in the README.
