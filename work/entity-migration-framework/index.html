Case study · 2025 · Open source · MIT

Version migration by graph, not by list.

Entities evolve. A UserV1 becomes a UserV2, which becomes a UserV3. Most migration systems make you register every pair of versions you might jump between. This one makes you register each migration once, as an edge in a graph, and finds the path from wherever you are to wherever you need to be.

The problem

Migrating from version 3 to version 7 should not require registering every combination between them.

A flat migration list forces you to write pairwise transformations: v3 to v4, v4 to v5, v5 to v6, v6 to v7, and then every other combination someone might need. It works until it does not. Miss a pair, and the migration silently fails at runtime. The graph-based approach fixes this by registering each migration once as a directed edge, then finding the shortest path from source to target. If a path does not exist, it fails loudly at registration time, not silently in production.

The approach

What I built.

  • Each migration is an edge: a generic type pairing a source version with a target version.
  • The registry is a directed graph. Path resolution is automatic.
  • Compile-time validated transformations — the migrate method returns the target type, not object.
  • Missing paths fail at registration, not at runtime.
  • Extracted from Singular Framework Core, usable standalone in any .NET project.

Technical deep dive

The choices that shaped it.

For engineers. The decisions behind the architecture, written down.

ADR-001Migration registry

Graph-based registry with path finding over a flat list

Problem
Entities evolve through many versions. Migrating from v3 to v7 requires composing v3 to v4, v4 to v5, v5 to v6, v6 to v7, and not every direct jump has a registered migration.
Options
Flat list applied sequentially · pairwise registrations · graph with path resolution.
Choice
Graph. Each migration registers as a directed edge between two versions. The framework finds the path from source to target.
Consequence
New versions register one edge, not every pairwise combination. Missing paths fail loudly at registration instead of silently at runtime.
Rejected because
A flat list grows quadratically with each new version, and pairwise registration turns schema evolution into busywork.
ADR-002Type safety

Compile-time validated transformations over runtime casting

Problem
A migration takes one type and returns another. Without generics, the return type is object and every consumer has to cast.
Options
Object-based migration · reflection-based mapping · generic migration pairing source and target types.
Choice
Generic. The compiler knows both the source and target type, and the migrate method returns the target type directly.
Consequence
No casts. No runtime type errors from migration mismatches. The compiler catches problems before the code runs.
ADR-003Packaging

Standalone package over an internal feature of Singular

Problem
The migration layer was built inside Singular Framework Core, but the problem it solves is not specific to single-object persistence.
Options
Keep it as an internal module · extract as a standalone library · duplicate into both.
Choice
Extract as a standalone NuGet package that Singular depends on.
Consequence
Any .NET project can use migration independently. Singular gets the same code without an internal fork, and the API surface stays minimal in both.

Lessons learned

What I'd do differently.

The honest section. Every project has one.

01

Document the path resolution algorithm before implementing it

I spent more time debugging edge cases in the graph traversal than I should have. Writing the algorithm down on paper first would have surfaced the tricky cases earlier.

02

Provide a default registry out of the box

The library requires you to build your own registry. That is flexible, but it is also friction. A sensible default would make the first run smoother.

03

Ship the documentation site earlier

The documentation is still incomplete. For a library, the docs are half the product. I would treat them as a first-class deliverable from day one.

FAQ

Common questions.

What is Entity Migration Framework? + −

Entity Migration Framework is a .NET library for migrating an entity through its version history. Instead of registering every pair of versions you might jump between, each migration is registered once as a directed edge in a graph. The framework finds the shortest path from the source version to the target version automatically.

Why use a graph instead of a flat list? + −

A flat list requires you to register every pairwise combination of versions, which grows quadratically as the schema evolves. A graph registers each migration once, and the framework composes them. It also fails loudly at registration time if a path does not exist, rather than failing silently at runtime.

Is it type safe? + −

Yes. Each migration is generic over its input and output types. The migration method returns the target type directly, so there are no runtime casts and no type errors from migration mismatches.

Can it be used outside of Singular? + −

Yes. It was extracted from the migration layer of Singular Framework Core, but it is a standalone library. Any .NET project that needs version-aware entity migration can use it independently.

Code sample

What using it looks like. 

public class UserV1ToV2 : IMigration<UserV1, UserV2>
{
    public UserV2 Migrate(UserV1 src) => new()
    {
        FullName = $"{src.FirstName} {src.LastName}"
    };
}

var manager = new MigrationBuilder<User>()
    .AddMigration<UserV1ToV2, UserV1, UserV2>()
    .Build();

var v2User = manager.Migrate<UserV1, UserV2>(v1User);
var v3User = manager.Migrate<UserV1, UserV3>(v1User); // composed automatically
