Home/Work/ Singular Framework Core

Case study · 2025 · Open source · MIT

A framework family for single-object storage.

Entity Framework handles tables of objects. Singular Framework Core handles the other case: one object, stored on its own, with the same CRUD interface you would expect from a database but for a config file, a local state file, or anything else that lives by itself.

The problem

Every project I built needed to store a single object. There was never a clean way to do it.

Load it. Validate it. Transform it. Encrypt it if it needs it. Serialize it. Write it somewhere. Version it when the shape changes. Migrate it when the version changes. Every one of those steps is the same across every project, and none of them are what the project is actually about. I kept rewriting the same six-step pipeline, badly, and I finally built the library I wished existed.

The approach

What I built.

  • Core library defines the interfaces. Every backend, serializer, and processor is a separate NuGet package.
  • CRUD-based API: Create, Read, Update, Delete — with async and bulk variants.
  • Four-phase storage pipeline: pre-processing → serialization → post-processing → storage.
  • Processing layers composable: encrypt, reshape, modify properties, or add custom transforms.
  • Generic over input and output types.

Technical deep dive

The choices that shaped it.

For engineers. The decisions behind the architecture, written down.

ADR-001Architecture

Interface-first package family over a single monolithic library

Problem
Support multiple storage backends, serialization formats, and encryption algorithms without forcing every consumer to pull in everything.
Options
One library with everything · core + extension packages · DI container in one assembly.
Choice
Core defines interfaces. Every backend is a separate NuGet package. Consumers install only what they use.
Consequence
Package count went from 1 to 5+. Bundle size for typical consumers dropped to what they actually call. Third-party extension became possible without forking.
Rejected because
A single monolithic library would have been simpler to publish, but it would have forced every consumer to pull in code they never call.
ADR-002Processing pipeline

Four-phase composable pipeline over a fixed serialization chain

Problem
Different projects need different transforms: encrypt the payload, reshape the bytes, modify properties before storage. A fixed chain could not cover all of them.
Options
Hard-code serialization · expose a serializer interface only · four-phase pipeline with pluggable processors at each stage.
Choice
Four phases — pre-processing, serialization, post-processing, storage — each with its own interface. Any processor can be inserted at any stage.
Consequence
Encryption became a processor. Binary reshaping became a processor. Property modification became a processor. Adding a new transform is a DI change, not a library fork.
ADR-003Generic typing

Generic over input and output

Problem
The stored format is not always the in-memory format. A model might serialize to JSON, BSON, or a custom binary format depending on the backend.
Options
Fixed output type · object as output · generic output type.
Choice
Generic. The input is the model. The output is the stored format. Both are defined by the consumer.
Consequence
The same core works for JSON, BSON, binary, or anything else. Serializers are interchangeable. The type system enforces the contract at compile time.

Lessons learned

What I'd do differently.

The honest section. Every project has one.

01

Publish the core first, add extensions later

I designed all the packages in parallel. In hindsight, publishing the core alone and letting the interfaces stabilize under real use would have made the extension API cleaner.

02

Write the interface documentation before the implementations

The core interfaces changed more than they should have once I started writing the concrete backends. Writing the docs first would have surfaced the awkward seams earlier.

03

Underestimated version coordination across packages

Five packages means five version numbers, five changelogs, and a compatibility matrix. It is manageable, but I would build tooling for it earlier next time.

Comparison

When to use Singular vs alternatives

Singular is not the right tool for every problem. Here is where it fits and where it does not.

FAQ

Common questions.

What is Singular Framework Core? + −

Singular Framework Core is a .NET library for storing and managing a single object independently — such as a config file, a local state file, or a user preferences object. It provides a CRUD-based interface over a composable pipeline of serialization, encryption, and storage layers, so the same code works whether the object ends up in a file, in the cloud, or in memory.

How is it different from Entity Framework Core? + −

Entity Framework Core manages tables of objects — relational data with rows, columns, and joins. Singular Framework Core manages a single object stored on its own, with no relations. They solve different problems and can be used side by side in the same project.

Can I use it with any storage backend? + −

Yes. The core library defines only the interfaces. Storage is provided by extension packages — file system, and soon cloud and in-memory. Any third party can add a new backend by implementing the storage interface.

Does it support encryption? + −

Yes. Encryption is a composable processor in the pipeline. Any symmetric algorithm in the .NET base class library works through the same interface, and the pipeline can chain multiple processors — encrypt, then reshape, then store.

What license is it under? + −

MIT. Free for commercial and personal use.

Code sample

What using it looks like.

C# 
public class AppConfig
{
    public string ApiKey { get; set; }
    public int TimeoutSeconds { get; set; }
}

var singular = new Singular<AppConfig, string>(
    serializer: new NewtonsoftJsonSerializer<AppConfig>(),
    storage: new FileSystemTextRepository("config.json"),
    processors: new IDataProcessorLayer<AppConfig, string>[]
    {
        new SymmetricEncryptorLayer<AppConfig, string>()
    }
);

await singular.CreateAsync(new AppConfig { ApiKey = "...", TimeoutSeconds = 30 });
var config = await singular.ReadAsync();
await singular.UpdateAsync(new AppConfig { ApiKey = "...", TimeoutSeconds = 60 });
await singular.DeleteAsync();
